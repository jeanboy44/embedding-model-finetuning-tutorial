# 전문가 검토

검토는 서브에이전트에게 맡긴다. 역할마다 따로 띄우고, 같은 문서와 이 저장소 맥락(아래)을 준다. 검토 원문은 `reviews/<단계>_<역할>_expert.md`로 저장한다(예: `reviews/plan_methodology_expert.md`). 실제 예시는 `experiments/archive/002_hard_negatives/reviews/`에 있다.

검토자는 문서를 고치지 않는다. 지적만 한다. 문서에 적힌 숫자는 믿지 말고, 중요한 것 몇 개는 원 데이터 · 결과 JSON을 열어 직접 다시 계산해 확인한다. 같은 계열 모델이 쓰고 검토하면 같은 곳을 놓치기 쉽기 때문이다. 반영은 바퀴를 도는 에이전트가 하고, 문서 끝 "검토 반영" 표에 적는다.

## 모든 검토자에게 주는 맥락

- 모델: multilingual-e5-small 하나(다른 모델 · reranker · BM25 금지). 배포는 인터넷 없는 PC의 HTML 파일 하나.
- 데이터: 법령 54개 · 검색 문서 25,967개, LLM이 만든 질문 12,232개, 조 단위 분할(`data/splits_article/`).
- 규칙: 판정 · 채택은 dev로만. test는 바퀴 안에서 쓰지 않는다(반복이 다 끝난 뒤 최종 모델 한 번). 개선 = Δ ≥ 0.02 그리고 Δ > seed 범위. dev 표준오차는 √(p(1−p)/n)로 계산(dev 1,198문항이면 약 ±0.014). 오답 분석은 dev-a에서만 하고 dev-b는 집계만 본다. 제약 전부는 `references/constraints.md`를 함께 준다.
- 검토할 문서 경로와, 앞 단계 문서 경로.

검토 결과는 다음 형식으로 쓰게 한다: **치명적**(이대로 돌리면 결론을 믿을 수 없다) / **중요**(결론의 크기나 해석이 바뀔 수 있다) / **사소**. 지적마다 근거와 고치는 방법 한 줄.

## IR(검색) 검토 — 계획서 · 회고

- 가설이 오답 분석의 숫자와 이어지나. 닿는 실패 범위를 과장하지 않나.
- 검색 쪽 선행 연구(hard negative 채굴, 가짜 negative, 손실 함수 등)의 알려진 함정을 피했나.
- 지표가 질문에 맞나(R@5, 법령 평균, 판정 방식 doc/article/multi).
- 회고: 다음 가설 후보의 근거와 우선순위가 타당한가.

## 방법론 검토 — 계획서 · 회고

- **누수**: 새로 만드는 데이터에 dev · test의 문서나 질문이 섞이지 않나. 후보 풀을 train으로 제한했나.
- **교란**: 한 run에서 두 가지가 같이 바뀌지 않나. 대조군이 같은 코드 · 같은 스케줄인가.
- **잡음**: seed 수, 합격선이 seed 범위와 표준오차를 넘는가. 다중 비교 보정이 있나.
- **사전 등록**: 합격선 · run 구성 · 판정 기준이 결과 전에 고정됐나. 데이터에 따라 바뀌는 분기가 없나.
- test를 썼거나 test 결과가 문서에 들어가 있지 않나 (바퀴 안에서는 쓰면 안 된다).
- 회고: 결론이 근거보다 강하지 않은가, 철회해야 할 해석이 있나.

## 운영 검토 — 회고

- 비용(학습 시간, 판정 토큰)이 효과에 맞았나. 다음엔 무엇을 작게 먼저 시험할까.
- 재현: 설정 · 데이터 해시 · 명령으로 남이 같은 숫자를 낼 수 있나.
- 로깅 누락, 실행 중 사고(덮어쓰기, 모니터 만료, 실패한 run 재시작)와 막는 법.
- 배포 영향: 모델 크기 · 속도 · 최적화(ONNX · INT8 · 어휘 가지치기) 조건이 그대로인가.
