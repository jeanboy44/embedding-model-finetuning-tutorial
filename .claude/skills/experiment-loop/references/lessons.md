출처: `experiments/archive/002_hard_negatives/05_retro.md`, `reviews/`. 계획서를 쓰기 전에 훑고, 해당하는 항목을 계획서의 누수 점검 · 로깅 · 비용 칸에 반영한다.

## 결론을 흔든 것

| 일어난 일 | 왜 문제였나 | 막는 법 |
|---|---|---|
| 채굴 후보의 15~19%가 dev · test 쪽 문서였다 | 평가 정답을 학습 때 오답으로 보여 줘 평가가 엉뚱하게 움직인다 | 후보 풀을 train 문서로 제한하고, 제한 전후 비율을 기록한다 |
| 예전에 학습한 모델(epoch 6 스케줄)을 대조군으로 쓰려 했다 | 코드 · 스케줄 차이가 효과에 섞인다 | 대조군을 같은 코드 · 같은 epoch로 다시 학습, seed 3개 |
| 출처(LLM → 모델)와 개수(1 → 3)가 한 run에서 같이 바뀌었다 | 어느 쪽 효과인지 모른다 | 한 가지씩만 다른 run(C)을 추가해 효과를 나눈다 |
| B와 A가 "서로 다른 혼동을 고친다"고 해석했다 | 차이가 seed 잡음 수준이었다 | 단일 seed 차이를 해석하기 전에 대조군 seed 간 차이와 비교한다. 틀린 해석은 "(철회)"로 남긴다 |
| (003) 2차 반복 채굴로 상위 negative 3개를 직접 학습했더니 성능 정체/하락 | 고성능 모델의 Rank 2~4는 False Negative 및 난이도 과적합 위험 | Iterative Mining 시 상위 1~3위 직하위만 쓰지 않고 Rank 5~20 분산 샘플링 또는 점수대별 필터링을 둔다 |
| (004) 소형 Bi-Encoder에 재학습 없는 제로샷 메타데이터 헤더 부착 시 성능 하락 | Mean Pooling 임베딩에서 본문 벡터 희석 및 미학습 메타데이터(총칙·벌칙 등) 간섭 | 코퍼스 텍스트 포맷을 바꿀 때는 제로샷으로 인덱스만 바꾸지 말고 학습 셋도 동일 포맷으로 재학습한다 |
| (005) 상투적 장(Chapter) 이름 단순 결합은 제로샷 하락은 복원하나 대조군을 넘지 못함 | 단순 장 이름("총칙", "벌칙")은 정보량이 적어 본문 희석을 상쇄하지 못함 | 오답의 23%인 법률↔시행령 혼동을 풀려면 상투적 장 이름 대신 구체적인 위임 조문 링크(정규식 추출)를 활용한다 |

## 비용

| 일어난 일 | 막는 법 |
|---|---|
| 9,009쌍(agent 30개, 수백만 토큰)을 다 판정했는데 B가 A를 넘지 못했다 | 큰 판정은 300쌍 시범부터. 시범으로 "판정이 학습 결과를 바꾸나"를 먼저 본다 |

## 실행 · 로깅

| 일어난 일 | 막는 법 |
|---|---|
| A · C에서 학습 질문 81개가 조용히 빠졌다(negative 0개) | 생성 데이터를 만들 때 "negative 0개 질문 수"를 출력하고, 처리 규칙(범위 확장 · 기존 negative로 대체 · 빼기)을 계획서에 미리 적는다 |
| agent들이 공유 scratchpad에서 보조 스크립트를 서로 덮어썼다 | agent마다 전용 폴더. 출력 검증 스크립트를 작업 직후 자동으로 돌린다 |
| 실제 학습 행 수 · negative 0개 수를 로그에 바로 남기지 않았다 | run이 끝날 때 `runs/<실험>/summary.tsv`에 요약 한 줄, MLflow에도 |

| (012) 다른 세션이 `data/splits_article/`을 다시 만들면서 dev_a/b가 지워졌다 | dev_a/b는 dev에서 결정적으로 만들어지므로 `run_queue.py`가 시작할 때 다시 만든다. 쓰기 전에 질문 집합이 이전 평가와 같은지 확인한다 |
