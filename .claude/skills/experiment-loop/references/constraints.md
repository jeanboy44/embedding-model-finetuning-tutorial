# 제약 사항

바퀴에 참여하는 **모든 에이전트**(오답 분석 · 리서치 · 계획 · 검토)에게 이 파일을 그대로 준다. 제약은 실험으로 바꾸는 대상이 아니다. 제약을 바꿔야만 가설을 검증할 수 있으면 그 가설은 이번 바퀴에서 하지 않고, 오케스트레이터가 사람에게 보고한다.

각 항목의 "왜"를 같이 적었다. 애매한 경우는 "왜"를 기준으로 판단한다.

## 1. 모델 · 기술 (배포 조건에서 나온 것)

| 제약 | 왜 |
|---|---|
| 모델은 `intfloat/multilingual-e5-small` 하나. 학습 · 오답 캐기 · 판정 보조 어디에도 다른 임베딩 모델을 쓰지 않는다 | 배포 환경이 인터넷 없는 낮은 사양 PC이고, 최종 산출물은 이 모델을 줄인 30MB 파일 하나다 |
| reranker, BM25 · 키워드 검색 섞기, LLM 질문 확장, 검색 시 LLM 호출을 쓰지 않는다 | 배포 환경에서 돌 수 없다. 점수가 올라도 쓸 수 없는 결과다 |
| 모델 크기 · 출력 차원(118M, 384)을 바꾸지 않는다 | 7교시 최적화(가지치기 · INT8)와 8교시 HTML 배포가 이 크기를 전제로 한다 |
| 판정(가짜 오답 판정, 라벨 오류 판정 등)은 Claude 서브에이전트가 한다. 외부 LLM API를 쓰지 않는다 | 비용 · 키 관리, 재현성 |

## 2. 데이터와 평가셋 사용

| 제약 | 왜 |
|---|---|
| 분할은 `data/splits_article/`(조 단위). 분할 자체가 가설이 아니면 바꾸지 않는다 | 바퀴끼리 숫자를 비교하려면 같은 평가셋이어야 한다 |
| **새 학습 데이터의 모든 재료는 train 조에서만**: 정답 문서, 오답 후보 풀, 합성 질문을 만들 때 보여 주는 조문, 추가 정답 | dev · test 조가 학습에 들어가면 평가 정답을 미리 보여 주는 셈이다(002에서 오답 후보의 15~19%가 평가 쪽 문서였다) |
| 새 학습 질문은 dev · test 질문과 거의 같은 문장인지 검사하고, 걸리면 뺀다 | 문장 단위 누수 |
| **오답 분석은 dev-a에서만** 질문 원문 · 순위를 열어 본다. dev-b는 집계 숫자만 본다 (dev-a/b: dev를 조 단위로 고정 seed 반씩, 오케스트레이터가 만든다) | 틀린 질문을 보고 세운 가설은 그 질문에서 유리하게 나온다. dev-b에서도 오르는지 봐야 가설이 일반적이다 |
| run 선택 · epoch 선택은 dev로만 한다 | test를 보고 고르면 test가 더 이상 처음 보는 데이터가 아니다 |
| **test는 실험(바퀴) 안에서 쓰지 않는다.** 반복이 모두 끝나 최종 모델이 정해졌을 때 그 모델 하나만 **딱 한 번** 잰다. 바퀴 안의 판정 · 채택 · 보고는 전부 dev로 한다 | 바퀴마다 test를 보면 바퀴 수만큼 test로 고른 셈이 된다. 한 번만 봐야 최종 숫자가 처음 보는 데이터의 숫자로 남는다 |
| 분할 · 판정 방식이 바뀐 뒤 첫 바퀴는 기준 모델(학습 전 e5, 현재 최고)을 새 분할로 다시 재는 것부터 한다. 분할이 다른 숫자끼리 비교하지 않는다 | `experiments/README.md`의 옛 숫자는 법령 단위 분할 값이다 |
| 판정 파일(`--labels`)은 현재 분할에 맞는 것만 쓴다. 없으면 doc 판정으로 하고 그렇게 적는다 | 옛 dev 판정 파일은 법령 단위 dev용이다 |

## 3. 판정 (합격선)

계획서에 결과보다 먼저 적는다. 기본값은 아래이고, 계획서에서 더 엄격하게는 바꿔도 느슨하게는 바꾸지 않는다.

| 제약 | 왜 |
|---|---|
| 대조군은 같은 코드 · 같은 설정 · 같은 epoch 스케줄로 다시 학습, **seed 3개** | 예전 모델을 쓰면 코드 · 스케줄 차이가 섞인다. seed 흔들림의 크기를 알아야 한다 |
| 채택 후보는 **seed 2개 이상**으로 확인하고, 판정은 seed 평균끼리 비교한다 | 후보 쪽이 운 좋은 seed였을 수 있다 |
| 개선 = Δ(평균) ≥ 0.02 **그리고** Δ > 대조군 seed 범위 **그리고** 질문 단위 대응 검정(`ragkit paired-test`) CI 하한 > 0. 비교가 여럿이면 McNemar p에 Holm 보정 | 대응 검정 CI는 질문 표집 흔들림만, seed 범위는 학습 흔들림만 본다. 둘 다 넘어야 한다 |
| dev 표준오차는 √(p(1−p)/n)으로 계산해 적고, 그보다 작은 차이는 해석하지 않는다 | 고정 숫자는 분할이 바뀌면 틀린다(dev 1,198문항이면 약 ±0.014) |
| 법령 평균 R@5가 표준오차 이상 떨어지지 않고, 법령별 McNemar(Holm 보정)로 유의하게 나빠진 법령이 0개 | 특정 법령에서만 오른 결과를 막는다 |
| dev-b에서의 Δ를 따로 보고한다. dev-b에서 방향이 반대면 개선으로 보지 않는다 | 분석에 쓴 질문 밖에서도 오르는지 |
| 한 run에서 두 가지가 같이 바뀌면 하나씩만 다른 run을 둔다. 못 두면 묶음으로만 해석한다 | 어느 쪽 효과인지 모른다 |
| 계산량(학습 시간 · step 수)이 대조군과 다르면 기록하고, 차이가 크면 계산량을 맞춘 대조를 두거나 한계로 적는다 | 오답 3개는 같은 epoch여도 시간이 1.7배였다 |

## 4. 예산

| 제약 | 왜 |
|---|---|
| 한 바퀴 학습 run 8개 이하(대조군 3 + 후보 · 분리 run + 채택 확인 seed). 사람이 정하면 그 값 | 학습 한 번이 40~95분 |
| 판정 작업은 300쌍 시범부터. 시범에서 "판정이 결과를 바꾸나"를 본 뒤 전체 여부를 정한다 | 002에서 9,009쌍을 다 판정했는데 효과가 없었다 |
| 본 학습 전에 파일럿(`--max-steps 30 --limit 300 --no-dev-eval`) | 40분 뒤에 메모리 부족 · 손실 미감소를 알면 시간이 통째로 날아간다 |

## 5. 운영

| 제약 | 왜 |
|---|---|
| 실행 전 재현 점검: 학습 전 모델과 현재 최고 모델의 dev 값을 다시 재서 알려진 값과 맞는지 본다 | 평가 인덱스 캐시나 코드 변경으로 파이프라인이 몰래 바뀌는 걸 잡는다 |
| 채택 모델은 배포 형태(가지치기 + INT8)로 바꿔 dev를 한 번 재고, 오른 폭이 남는지 적는다 | 배포되는 건 줄인 모델이다. 양자화 방식에 따라 R@5가 0.514와 0.458로 갈린 적이 있다 |
| 서브에이전트마다 전용 작업 폴더. 공유 폴더에 보조 스크립트를 두지 않는다 | 002에서 서로 덮어썼다 |
| 실행 결과는 `runs/<실험>/`에, 진행은 `timeline.md`에, 지표 · 설정 · 문서는 MLflow에 남긴다. 대화 기억에만 있는 사실은 없는 것으로 본다 | 대화가 끊기거나 다른 에이전트가 이어받아도, 나중에 사람이 봐도 확인 · 재현할 수 있어야 한다 |
| 커밋 · 푸시는 하지 않는다. 사람이 요청할 때만 | |
| 기존 모델 · 분할 · 데이터 파일을 덮어쓰지 않는다. 새 산출물은 새 경로에 | |
