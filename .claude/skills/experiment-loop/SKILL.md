# 실험 한 바퀴 (성능 향상 실험 반복)

이 저장소의 목표는 작은 임베딩 모델 하나(e5-small)를 우리 질문 데이터로 학습해 법령 검색을 잘하게 만드는 것이다. 성능은 한 번에 오르지 않는다. **틀린 질문을 보고 → 가설을 세우고 → 미리 정한 기준으로 실험하고 → 결과를 판정하고 → 다음 가설로** 바퀴를 반복한다. 이 스킬은 그 바퀴 하나를 처음부터 끝까지 돌 때 쓴다.

바퀴의 가치는 점수가 아니라 **믿을 수 있는 결론**에 있다. 누수가 있었거나, 틀린 질문을 보고 세운 가설을 같은 질문으로 판정했거나, seed 잡음 안의 차이라면 그 결론은 다음 바퀴를 엉뚱한 곳으로 보낸다. 바퀴를 여러 번 돌수록 이런 낙관이 쌓이므로, 아래 제약과 역할 분리는 대부분 그걸 막으려고 있다.

## 제약 사항

**`references/constraints.md`가 이 바퀴의 제약 전부다.** 오케스트레이터는 시작할 때 읽고, 모든 서브에이전트에게 그 파일 경로를 넘긴다. 요약:

| 분류 | 핵심 |
|---|---|
| 모델 · 기술 | e5-small 하나. reranker · BM25 · LLM 확장 · 다른 모델 금지. 크기 · 차원 그대로 |
| 데이터 · 평가셋 | 조 단위 분할 고정. 새 학습 데이터 재료는 train 조에서만. 오답 분석은 dev-a에서만. 판정 · 채택 · 보고는 dev로만. **test는 바퀴 안에서 쓰지 않는다**(반복이 끝난 뒤 최종 모델 한 번) |
| 판정 | 대조군 seed 3, 채택 후보 seed 2 이상. Δ ≥ 0.02 · Δ > seed 범위 · 대응 검정 CI > 0 · 나빠진 법령 0 · dev-b에서도 같은 방향 |
| 예산 | 학습 run 8개 이하, 판정은 300쌍 시범부터, 본 학습 전 파일럿 |
| 운영 | 실행 전 재현 점검, 채택 모델은 배포 형태로도 재기, 에이전트별 전용 폴더, 커밋 금지 |

가설이 제약을 깨야만 검증된다면 그 가설은 하지 않는다. 깨지 않는 대안이 없으면 멈추고 보고한다.

## 역할

이 스킬을 쓰는 에이전트가 **오케스트레이터**다. 오케스트레이터는 문서를 직접 쓰기보다, 단계마다 맡은 에이전트를 띄우고 산출물을 확인하고 실행을 맡는다. 오답 분석 · 리서치 · 계획서를 서로 다른 에이전트에게 맡기는 이유는 두 가지다. 각 단계가 앞 단계의 문서만 근거로 삼게 되어 논리가 문서에 남고, 오답 분석에서 본 개별 질문이 계획 · 판정으로 새어 들어가는 것을 줄인다.

| 역할 | 하는 일 | 보는 것 | 쓰는 것 |
|---|---|---|---|
| 오케스트레이터 | 폴더 · dev-a/b 만들기, 재현 점검, 에이전트 띄우기와 산출물 확인, 학습 · 평가 실행, 합격선 계산, 결과 · 회고 정리, ledger · README | 전부 | `runs/<실험>/` 전체, `04_results.md`, `05_retro.md`, MLflow 기록 |
| 오답 분석 에이전트 | 현재 최고 모델의 실패 분석, 라벨 오류 표본 판정, 가설 후보 | 모델, dev-a 질문별 결과, train 데이터 | `00_error_analysis.md` |
| 리서치 에이전트 | 가설 후보별 근거와 효과 크기 | `00` 문서, 문헌 | `01_research.md` |
| 계획 에이전트 | 가설 확정, run 구성, 합격선, 누수 점검, 비용 | `00` · `01` 문서, 제약, `lessons.md` (dev 질문별 결과는 보지 않는다) | `02_plan.md` |
| 검토 에이전트 | 계획서(IR · 방법론), 회고(IR · 방법론 · 운영) 검토 | 검토할 문서와 앞 단계 문서, 필요하면 데이터 파일 | `reviews/*.md` |

서브에이전트에게 줄 것: 이 SKILL.md 경로, `references/constraints.md`, 맡은 단계의 템플릿(`references/templates.md`의 해당 절), 실험 폴더 경로, 앞 단계 문서 경로, **전용 작업 폴더**(`runs/<실험>/work/<역할>/`). 산출물을 받으면 오케스트레이터가 템플릿의 칸이 다 찼는지, 숫자가 원 데이터와 맞는지 몇 개 골라 확인한다. 빠졌으면 같은 에이전트에게 고쳐 달라고 돌려보낸다.

## 기록: 에이전트의 기억이 사라져도 전부 남게

바퀴의 이력은 에이전트의 대화 기억이 아니라 **파일과 MLflow**에 있어야 한다. 대화가 끊기거나 요약돼도, 다른 에이전트가 이어받아도, 몇 달 뒤 사람이 보더라도 무엇을 왜 했고 어떤 숫자가 어디서 나왔는지 확인하고 같은 숫자를 다시 낼 수 있어야 한다. 기억에만 있는 사실은 없는 것으로 본다.

| 위치 | 담는 것 |
|---|---|
| `experiments/<번호>_<이름>/` | 사람이 읽는 문서: `00`~`05`, `reviews/` |
| `runs/<번호>_<이름>/` | 실행 결과 전부 (아래) |
| MLflow (실험 이름 `loop/<번호>_<이름>`) | 학습 · 평가 run 기록, 지표, 설정, 문서 사본 |

`runs/<번호>_<이름>/` 구성:

```
manifest.json      실험 메타: 번호 · 이름 · 가설 · 분할 · 기준 모델 · git commit · 시작/끝 시각 · 상태 · 결정 · MLflow 실험 이름
timeline.md        진행 일지 (덧붙이기만 한다): 시각 · 한 일 · 결과 · 다음 할 일
queue.tsv          run 대기열: run · 상태(대기 · 실행 중 · 완료 · 실패) · 시작 · 끝 · 로그 경로
summary.tsv        run마다 한 줄 요약 (실행 단계 참고)
data_digest.json   분할 · 코퍼스 · 새로 만든 데이터의 sha256과 행 수, git commit, uv.lock 해시, 라이브러리 버전
decision.json      합격선 계산 결과
<run>/             config.yaml · command.sh(실행한 명령 그대로) · train.log · train_meta.json
                   eval_dev.json · eval_dev_b.json · paired_test.json · paired_test_dev_b.json · eval_deploy.json
analysis/          오답 분석 재료 (상위 k 결과, 집계 출력 원문)
data/              새로 만든 학습 데이터 (캔 오답, 추가 질문 등)
work/<역할>/       서브에이전트 작업 폴더
```

- **timeline.md는 단계가 바뀔 때, run을 띄우고 끝날 때, 계획을 바꿀 때마다** 한 줄 덧붙인다. 이어받는 에이전트는 이 파일과 `queue.tsv`만 읽고 어디서부터 이어 갈지 알 수 있어야 한다.
- 명령은 `command.sh`에 실제로 친 그대로 남긴다. 숫자는 손으로 옮겨 적지 말고, 문서에는 어느 파일에서 왔는지 경로를 붙인다.
- **MLflow는 항상 켠다.** 바퀴를 시작할 때 `MLFLOW_TRACKING_URI`가 없으면 `sqlite:///mlruns/mlflow.db`로 잡고, `MLFLOW_EXPERIMENT=loop/<번호>_<이름>`을 같이 준다. 그러면 `ragkit train` · `evaluate`가 run을 스스로 기록한다. 단계가 끝날 때마다(그리고 바퀴 끝에) `uv run --extra mlflow python .claude/skills/experiment-loop/scripts/log_experiment.py <번호>_<이름>`으로 바퀴 run(가설 · 결정 · 문서)과 학습 run별 지표 · 설정 · 결과 파일을 올린다. 다시 실행해도 같은 run에 이어 기록된다.
- 서버 화면은 `uv run --extra mlflow mlflow server --backend-store-uri sqlite:///mlruns/mlflow.db --port 5050`(5000은 macOS AirPlay가 쓴다).

## 자원 관리 · 모니터링 (오케스트레이터)

학습은 이 기계의 GPU(MPS) 하나에서 돌고, 백그라운드 작업이 끝났다는 알림은 띄운 에이전트에게만 온다. 그래서 자원 관리와 감시는 오케스트레이터가 맡는다.

| 대상 | 규칙 |
|---|---|
| 학습 순서 | run은 한 번에 하나씩 `queue.tsv` 순서대로. 실행 스크립트가 run마다 상태를 갱신한다 |
| 감시 | 백그라운드로 띄우고 끝나면 알림을 받는다. 짧은 간격으로 확인하지 않는다. 로그가 15분 넘게 안 늘면 멈춘 것으로 보고 원인을 본다 |
| 학습 이상 | 손실이 NaN이거나 줄지 않으면 그 run을 멈추고 기록한다. 다시 시도는 한 번까지 |
| 자원 기록 | run마다 학습 시간 · step 수 · 최대 메모리 · 모델 크기를 `summary.tsv`와 MLflow에 |
| 디스크 | 모델 하나가 약 470MB. 바퀴가 끝나면 남은 디스크와 모델 목록을 보고에 적는다. 지우지는 않는다(지울지는 사람이 정한다) |
| 서브에이전트 | 동시에 5개까지. 큰 작업(판정 등)은 조각으로 나누고 조각마다 결과 파일을 남겨, 사용량 한도로 멈춰도 남은 조각만 다시 돌린다 |
| 예산 | 실행 시간 · 판정 쌍 수를 누적해 `timeline.md`에 적고, 계획서 예산의 80%에 닿으면 남은 run을 줄일지 판단해 기록한다 |

## 진행 방식: 끝까지 자율

한 바퀴를 사람 승인 없이 끝까지 돈다. 사람은 나중에 문서만 읽어도 무엇을 왜 정했는지 따라올 수 있어야 한다. 다음 경우에만 멈추고 보고한다.

- 가설 검증에 제약을 깨야 하고 대안이 없을 때
- 계획서 검토의 치명적 지적이 계획을 고쳐도 안 풀릴 때
- 예산을 넘길 것 같을 때
- 재현 점검에서 알려진 값이 안 나올 때, 같은 오류로 학습 · 평가가 두 번 실패했을 때

멈출 때도 그때까지의 문서를 남기고, 진행 중인 단계 문서 맨 위에 어디서 왜 멈췄는지 적는다.

## 바퀴

### 준비 (오케스트레이터)

1. `experiments/README.md`의 실험 표와 **가설 대기 목록**, ledger, 직전 바퀴의 `05_retro.md`를 읽는다. 기각된 가설을 다시 시험하지 않는다.
2. 새 폴더 `experiments/<번호>_<이름>/`와 `runs/<번호>_<이름>/`를 만들고 `manifest.json` · `timeline.md`를 시작한다. MLflow 설정(위 기록 절)을 잡는다. 번호는 README 표의 다음 빈 번호. 이름은 가설이 정해진 뒤 붙여도 되고, 그때 두 폴더 이름을 함께 바꾼다.
3. dev-a/b가 없으면 만든다: dev를 조 단위로 seed 고정해 반씩, `data/splits_article/dev_a.jsonl` · `dev_b.jsonl`. 이미 있으면 그대로 쓴다(바퀴마다 바꾸지 않는다).
4. **재현 점검**: 학습 전 e5와 현재 최고 모델을 dev로 다시 재서(`runs/<실험>/baseline_check/`) 알려진 값과 맞는지 본다. 분할이 바뀐 뒤 첫 바퀴라면 이 값이 새 기준선이 된다.

### 0. 오답 분석 (오답 분석 에이전트)

- 현재 최고 모델로 dev-a 질문마다 상위 50개를 `runs/<실험>/analysis/`에 저장한다(`references/tools.md`의 `dump_topk.py`). 집계 스크립트와 출력 원문도 같은 곳에 둔다.
- 실패(top-5 밖)를 **1위 오답과 정답의 관계**(다른 법 · 같은 테마 / 다른 법 · 다른 테마 / 같은 법 · 법률↔시행령 / 같은 법 · 같은 종류 다른 조 / 같은 조의 다른 조각)와 **정답 순위**(6~10 · 11~30 · 31~100 · 100위 밖)로 묶는다. 질문 유형 · 법령 · 단어 겹침별로도 본다.
- **라벨 오류 표본**: 실패 30~50개를 골라 "1위 결과가 사실 이 질문의 답인가"를 판정한다. 생성 질문은 정답이 하나로 고정돼 있어 실패의 상당수가 라벨 문제일 수 있다(002 판정에서 상위 후보의 29%가 진짜 오답이 아니었다). 이 비율이 모델 문제와 데이터 문제를 가른다.
- **틀린 질문 10개 이상을 직접 읽고** 몇 개는 원문으로 남긴다.
- 학습 데이터 쪽: hard negative의 출처, 현재 모델 기준 순위(이미 50위 밖이면 학습 신호가 없다).
- 끝에 **가설 후보 2~3개**를 근거 숫자 · 닿는 실패 범위 · 대략의 비용과 함께 적는다. 고르는 것은 계획 에이전트의 몫이다.

### 1. 리서치 (리서치 에이전트)

가설 후보마다 같은 문제를 다룬 논문 · 보고서의 **방법 · 조건 · 효과 크기**를 표로 모은다. 우리 상황(작은 모델, 한국어 법령, LLM 생성 질문)과 다른 점, 알려진 함정을 적는다. 근거가 없으면 없다고 쓴다. 후보 사이의 우선순위 의견을 근거와 함께 낸다.

### 2. 계획서 (계획 에이전트) — 결과를 보기 전에

- 후보 중 하나를 **가설** 한 문장으로 확정한다: 무엇을 바꾸면, 어떤 지표가, 왜 오르는가. 틀릴 수 있는 문장이어야 한다.
- **제약 확인 표**: `constraints.md`의 항목마다 이 계획이 어떻게 지키는지 한 줄씩. 특히 새 데이터의 재료가 train 조에서만 오는지.
- 고정한 것 · 바꾸는 것, run 구성(대조군 seed 3, 후보, 효과를 나누는 run, 채택 확인 seed), 파일럿.
- 합격선은 `constraints.md` 3절 기본값 이상으로. 계산량이 다르면 어떻게 다룰지.
- 하이퍼파라미터가 효과와 얽힐 수 있으면(예: 데이터를 바꾸면 최적 lr이 바뀜) 대조군과 후보에 같은 작은 탐색을 주거나 한계로 적는다.
- 누수 점검 목록, 로깅, 예상 시간 · 비용, 하지 않는 것.

초안이 오면 오케스트레이터가 **IR · 방법론 검토 에이전트**를 각각 띄운다(`references/reviewers.md`). 검토 원문은 `reviews/`에 두고, 계획 에이전트에게 반영을 맡긴다. 계획서 끝 "검토 반영" 표에 지적마다 반영 여부와 이유가 남아야 한다.

### 3. 실행 (오케스트레이터)

- 파일럿을 먼저 돌린다. 메모리 · step당 시간 · 손실 방향이 정상이면 본 학습.
- run마다 `runs/<실험>/<run>/config.yaml`과 `command.sh`를 쓰고, `uv run ragkit train <config> --splits data/splits_article`. 모델은 `models/finetuned/<번호>_<이름>[_<run>]`. 새로 만든 학습 데이터는 `runs/<실험>/data/`에.
- run이 끝날 때마다 `summary.tsv`에 한 줄(run · 학습 행 · negative 0개 질문 · 시간 · step 수 · 최대 메모리 · best epoch · dev R@5 · dev-b R@5 · 대조군 대비 Δ), `timeline.md`에 한 줄, 그리고 `log_experiment.py`로 MLflow에 올린다.
- 공식 dev 평가와 대응 검정(`references/tools.md`), 결과 JSON은 run 폴더에. `data_digest.json`에 해시 · 행 수 · git commit · uv.lock 해시 · 라이브러리 버전.
- 계획에 없던 차이(빠진 질문, 바뀐 행 수, 실패한 run)는 바로 기록한다.
- 합격선을 통과한 후보 중 채택할 run은 두 번째 seed로 다시 학습해 확인한다.
- 채택 모델을 배포 형태(가지치기 + INT8)로 바꿔 dev를 한 번 잰다.

### 4. 결과 (오케스트레이터)

- 맨 위에 **결론 한 문단**: 합격 여부, 채택 run, 크기(seed 평균 Δ와 CI), dev-b에서도 같은 방향인지. 근거보다 강하게 쓰지 않는다.
- 결과표, epoch별 dev, 해석(섞인 효과는 나눠서), 고친 질문 · 새로 틀린 질문, 실패 유형 변화, 배포 형태에서의 값, 계획 대비 차이.
- 철회한 해석은 지우지 않고 "(철회)"로 남긴다.
- test는 쓰지 않는다. 결과 문서의 모든 숫자는 dev다.

### 5. 회고 (오케스트레이터 + 검토)

- 잘된 것 / 아쉬운 것과 개선(실험 방법 · 로깅 · 오답 분석), 다음 바퀴 규칙, **다음 가설 후보**(근거 · 예상 효과 · 비용 순위).
- IR · 방법론 · 운영 검토를 받아 반영한다.
- `experiments/README.md`의 실험 표 · 진행 표에 한 줄, **가설 대기 목록**에 이번 결과(채택 / 기각 / 보류)와 새 후보를 반영한다.
- `references/lessons.md`에 새로 생긴 실수와 막는 법이 있으면 한 줄 더한다.
- `manifest.json`에 상태 · 결정 · 끝 시각을 적고, `log_experiment.py`로 마지막으로 올린다.

## 반복을 끝낼 때: test 한 번

바퀴를 반복하다가 사람이 "여기서 끝"이라고 하면(또는 사람이 정한 종료 조건에 닿으면), 그때까지의 최고 모델 **하나만** test로 딱 한 번 잰다. 학습 전 e5와 기본 실험 001도 같은 test로 함께 재서 한 표에 놓는다. `experiments/ledger.tsv`에 적고, 이 숫자로는 더 이상 무엇도 고르지 않는다. 이 단계는 바퀴 안에서 오케스트레이터가 스스로 시작하지 않는다.

## 바퀴를 마치면 보고할 것

사람에게 다섯 줄 안쪽으로: 가설, 합격 여부와 채택 run, dev Δ(seed 평균)와 CI · dev-b 방향, 배포 형태에서 남은 폭, 다음 가설 후보 1순위. 문서 경로, `runs/` 경로, MLflow 실험 이름을 붙인다. 남은 디스크와 이번 바퀴에서 만든 모델 목록도 적는다. 두 바퀴 연속 기각이면 다음 바퀴 전에 방향을 사람과 상의하자고 적는다.
