예전에는 모델을 만들면 파일과 torch 환경을 그대로 넘기는 데서 DS의 일이 끝났습니다. 무겁다는 피드백이 와도 줄이는 건 다른 팀 일이었죠. 지금은 AI 도구 덕분에 변환, 양자화, 가지치기를 DS가 직접 해 보고, 정확도를 얼마나 잃고 무엇을 얻는지 숫자로 판단할 수 있습니다.

다시 학습하지 않는다. 학습 때의 optimizer(AdamW)와도 다른 이야기다. 줄인 뒤에는 정확도를 꼭 다시 잰다.

오늘 말하는 최적화가 무엇인지부터 정리합니다. 학습은 모델이 더 잘 맞히도록 가중치 값을 바꾸는 일이었습니다. 배포 최적화는 이미 다 만든 모델을, 같은 답을 내면서 더 싸고 빠르게 돌게 하는 일입니다. 다시 학습하지 않고, 모델을 담는 형식, 숫자를 몇 비트로 저장하는지, 모델이 들고 있는 어휘를 바꿉니다. 학습할 때 들은 optimizer, AdamW와 이름은 비슷하지만 전혀 다른 이야기입니다. 그리고 줄이면 정확도가 떨어질 수 있으니, 줄인 뒤에는 반드시 정확도를 다시 잽니다. 크기와 정확도를 같이 재는 것, 이게 오늘 내내 할 일입니다.

왜 필요한가

만들 때는 한 번, 쓸 때는 매번

학습은 GPU 한 대에서 한 번 끝난다. 서비스는 질문마다, 서버마다, 날마다 돈다. 임베딩 모델은 질문이 올 때마다 한 번, 문서를 새로 넣을 때마다 또 돈다.

비용

메모리가 곧 서버 크기다. 서버를 여러 대 띄우면 그만큼 곱해진다

속도

검색은 답변 앞 단계라 사용자는 둘을 합친 시간을 기다린다. 서버를 새로 켤 때는 로딩 시간도 기다린다

놓을 수 있는 곳

GPU 없는 서버, 동료 노트북, 인터넷이 막힌 사내망. torch를 깔기 어렵거나 너무 무거운 곳

이걸 했기에, 3교시의 단일 HTML 임베딩 검색기가 가능했다

ONNX 변환 → 브라우저(JS) 위에서 실행

양자화 + 어휘 가지치기 → 모델 30MB

왜 굳이 줄일까요. 학습은 GPU 한 대에서 한 번 하면 끝납니다. 그런데 서비스는 질문이 올 때마다, 띄운 서버마다, 매일 돕니다. 임베딩 모델은 질문마다 한 번, 문서를 새로 넣을 때마다 또 돕니다. 그래서 작은 차이가 계속 곱해집니다. 첫째는 비용입니다. 모델이 쓰는 메모리가 서버 크기를 정하고, 서버를 여러 대 띄우면 그대로 곱해집니다. 둘째는 속도입니다. 검색은 LLM 답변 앞 단계라 사용자는 검색과 답변을 합친 시간을 기다립니다. 요청이 몰릴 때 서버를 새로 켜면 모델 로딩 시간도 기다려야 합니다. 셋째는 놓을 수 있는 곳입니다. GPU 없는 서버, 동료 노트북, 인터넷이 막힌 사내망처럼 torch를 통째로 깔기 어려운 곳에도 모델을 보내야 할 때가 있습니다. 그리고 3교시에 보여 드린 HTML 파일 하나짜리 검색기를 기억하시나요? 더블클릭하면 Python도 서버도 인터넷도 없이 브라우저에서 법령을 검색하던 그 파일입니다. 그게 가능했던 게 바로 오늘 할 최적화 덕분입니다. 모델을 ONNX로 바꿨기 때문에 브라우저의 JavaScript 위에서 돌 수 있었고, 양자화에 어휘 가지치기까지 더해 모델을 30MB로 줄였기 때문에 HTML 파일 하나에 담을 수 있었습니다.

아직은 아닐 때 정확도가 목표에 못 미칠 때, 사용자가 적은 내부 실험, GPU 서버가 이미 넉넉할 때. 줄이기는 정확도를 지킬 때만 의미가 있다.

그럼 언제 필요할까요. 모델이 어디에 놓이느냐가 정합니다. 동료 노트북이나 사내 PC에 CLI로 깔아 준다면 설치 크기와 모델 파일이 문제라 torch를 빼는 ONNX 변환과 어휘 가지치기가 먼저입니다. GPU 없는 CPU 서버라면 메모리와 지연이, 요청에 따라 서버를 자주 켰다 껐다 한다면 로딩 시간이, 서버를 여러 대 띄운다면 메모리, 곧 서버 비용이 문제입니다. 반대로 문서를 대량으로 자주 다시 임베딩해야 한다면 처리량이 중요한데, 이때는 줄인 모델이 오히려 느릴 수 있어서 GPU와 배치 크기를 먼저 봅니다. 이건 뒤 비교표에서 숫자로 확인합니다. 아직 최적화할 때가 아닌 경우도 있습니다. 정확도가 목표에 못 미친다면 줄이기보다 정확도가 먼저고, 사용자가 적은 내부 실험이나 GPU가 넉넉한 환경이라면 굳이 할 필요가 없습니다. 오늘은 이 중 우리 상황, 즉 동료에게 CLI로 깔아 주고 CPU 서버에 API로 띄우는 경우를 기준으로 줄여 봅니다.

형식 ≠ 엔진

ONNX는 파일 형식, ONNX Runtime은 그걸 돌리는 Microsoft의 엔진. 연산 사전의 판 번호를 opset이라 부른다

Open Neural Network Exchange · 2017년 Facebook과 Microsoft가 발표 · 2019년부터 Linux Foundation AI & Data 프로젝트

ONNX가 무엇인지부터 짚겠습니다. Open Neural Network Exchange의 줄임말로, 신경망 모델을 담는 표준 파일 형식입니다. 2017년에 Facebook과 Microsoft가 함께 발표했고, 지금은 Linux Foundation 산하 프로젝트입니다. 비유하자면 문서의 PDF입니다. 워드 파일은 워드가 있어야 열리지만 PDF는 어디서나 열리죠. PyTorch 모델은 가중치만으로는 돌지 않고, 그 모델을 정의한 Python 코드가 있어야 합니다. ONNX로 바꾸면 행렬곱, 덧셈, 소프트맥스 같은 연산이 어떤 순서로 이어지는지, 즉 계산 그래프와 가중치가 한 파일에 들어갑니다. 그래서 Python 코드 없이도 돕니다. 변환은 예시 문장을 넣고 모델을 한 번 돌리면서 지나간 연산을 기록하는 방식이고, 배치 크기나 문장 길이처럼 매번 달라지는 축은 바뀔 수 있다고 표시해 둡니다. 헷갈리기 쉬운 점 하나. ONNX는 파일 형식이고, ONNX Runtime은 그 파일을 돌리는 Microsoft의 엔진입니다. Intel의 OpenVINO나 NVIDIA의 TensorRT 같은 다른 엔진도 ONNX 파일을 읽습니다.

메모리는 셋을 올린 것에 계산 중간값(배치 × 문장 길이 × 차원)이 더해진다. 긴 문서를 크게 묶으면 모델보다 중간값이 더 커진다.

세 가지를 따로 재야 어디를 줄일지 보인다

조금 더 기술적으로 들어가 보겠습니다. 모델을 배포한다고 하면 보통 모델 파일만 떠올리는데, 실제로 옮겨지는 건 세 덩어리입니다. 첫째는 런타임, 모델을 실제로 계산하는 엔진입니다. PyTorch냐 ONNX Runtime이냐에 따라 쓸 수 있는 언어와 설치 크기가 완전히 달라집니다. 둘째는 모델 파일인데, 크기는 단순합니다. 파라미터 수 곱하기 숫자 하나의 바이트 수입니다. 파라미터가 1억 개면 32비트 실수로 400MB, 16비트로 200MB, 8비트 정수로 100MB입니다. 양자화가 파일을 4분의 1로 줄이는 이유가 이겁니다. 셋째는 토크나이저입니다. 문장을 토큰 번호로 바꾸는 사전인데, 다국어 모델은 어휘가 수십만 개라 이 파일만 10MB가 넘습니다. 메모리는 이 셋을 올린 것에 계산하면서 생기는 중간값이 더해집니다. 중간값은 배치 크기, 문장 길이, 차원에 비례해서, 긴 문서를 한꺼번에 많이 넣으면 모델보다 커지기도 합니다.

지금까지 이야기한 걸 층으로 쌓아 보겠습니다. 맨 아래는 운영체제입니다. 윈도우든 맥이든 리눅스든 같은 OS 위에서도, 그 위에서 어떤 언어로 프로그램을 짜느냐가 다릅니다. Python으로 서버나 CLI를 만들 수도 있고, C#으로 사내 데스크톱 앱을 만들 수도 있고, JavaScript로 브라우저에서 돌릴 수도 있습니다. 그 위가 런타임입니다. 주황색 PyTorch는 Python 칸에만 있습니다. 설치가 약 560MB이고, 모델 파일만으로는 안 되고 모델을 정의한 Python 코드까지 같이 있어야 돕니다. 파란색 ONNX 경로를 보면, 런타임은 언어마다 따로 깔지만 이름은 모두 ONNX Runtime이고, 맨 위의 model.onnx는 같은 파일 하나입니다. Python에서는 pip로 77MB, C#에서는 NuGet으로 16에서 44MB, 브라우저에서는 14MB짜리 wasm을 한 번 내려받습니다. 그러니까 모델을 Python 밖으로 보내야 한다면 ONNX로 바꾸는 게 출발점이 됩니다.

PyTorch는 사실상 Python 전용이다. ONNX는 표준 형식이라 같은 모델 파일을 Python · C# · 브라우저(JS)에서 같은 엔진으로 돌린다.

2026-10 기준 torch 2.14 · onnxruntime 1.30 · NuGet 네이티브 = win-x64 16 · linux-x64 29 · osx-arm64 44MB (패키지 전체는 모든 OS 합쳐 157MB)

런타임 크기를 환경별로 놓아 봤습니다. Python에서 PyTorch를 CPU판으로 깔면 torch 폴더만 약 560MB입니다. 리눅스에서 그냥 pip install torch를 하면 GPU용 CUDA 라이브러리까지 따라와서 수 GB가 됩니다. GPU 없는 서버에서는 전부 쓰지 않는 짐입니다. 같은 일을 ONNX Runtime으로 하면 휠이 23MB 정도, 설치해도 77MB 정도입니다. 더 중요한 차이는 언어입니다. PyTorch는 사실상 Python 안에서만 돕니다. ONNX는 모델을 표준 형식으로 저장한 것이라, 같은 model.onnx 파일을 C#에서는 NuGet 패키지로, 브라우저에서는 WebAssembly로 돌릴 수 있습니다. C#은 운영체제별 네이티브 라이브러리 하나가 16에서 44MB, 브라우저는 14MB 정도의 wasm 파일을 한 번 내려받습니다. 그래서 Python 밖으로 나가야 한다면 ONNX 변환은 선택이 아니라 필수입니다.

오늘 ONNX를 고른 이유: 언어 · OS · 하드웨어를 가장 넓게 덮고, OpenVINO · TensorRT도 ONNX에서 출발한다.

ONNX만 있는 건 아닙니다. 대표적인 선택지를 정리했습니다. 가장 쉬운 건 변환하지 않고 CPU판 torch로 그대로 내보내는 겁니다. Python 서버이고 빨리 내보내야 하면 충분합니다. Intel CPU 서버라면 Intel의 OpenVINO가, NVIDIA GPU라면 TensorRT가 각 하드웨어에 맞춰 더 빠르게 돌려 줍니다. 둘 다 ONNX 파일을 입력으로 받습니다. 모바일 앱 안에 넣으려면 Apple의 Core ML, Google의 LiteRT, 예전 이름 TensorFlow Lite가 있습니다. LLM을 로컬에서 돌릴 때 많이 쓰는 llama.cpp도 2024년부터 우리 모델과 같은 XLM-RoBERTa 계열 임베딩 모델을 GGUF 형식으로 돌립니다. 코드를 짜지 않고 임베딩 API 서버만 필요하다면 Hugging Face의 Text Embeddings Inference를 컨테이너로 띄우면 됩니다. 마지막으로 정적 임베딩은 모델을 단어별 벡터 표로 증류해서 트랜스포머 계산 자체를 없앱니다. 아주 작고 빠르지만 문맥을 보지 못해 정확도를 잃습니다. 오늘 ONNX를 고른 건 언어, 운영체제, 하드웨어를 가장 넓게 덮고, OpenVINO나 TensorRT로 가더라도 ONNX에서 출발하기 때문입니다.

정리하면, 모델이 어디서 도느냐가 어디까지 최적화해야 하는지를 정합니다. GPU가 있는 Python 서버라면 ONNX 변환은 선택이고, 줄이기보다 처리량이 먼저입니다. CPU 서버라면 torch를 빼는 ONNX 변환을 권하고, 메모리나 서버 대수가 문제일 때 INT8을 더합니다. C# 앱 안에 모델을 넣는다면 ONNX는 필수고, 모델 크기가 앱 설치 크기에 그대로 더해집니다. 브라우저나 모바일이라면 변환도 줄이기도 필수입니다. 사용자가 모델을 내려받는 시간이 곧 첫 화면을 기다리는 시간이기 때문입니다. 다른 길도 있습니다. 모델을 API 서버 하나로 감싸면 C#이든 웹이든 HTTP만 부르면 되니까 런타임 고민은 서버 한 곳에만 남습니다. 다만 네트워크가 없는 곳에서는 쓸 수 없죠. 오늘은 CPU에서 도는 Python API 서버와 동료 노트북의 CLI를 기준으로 줄여 보겠습니다.

전문가가 아닌데도 할 수 있는 이유는, 역시 AI입니다. 다만 AI라서 무엇이든 되는 건 아니고, 이 일이 AI가 잘하는 종류의 일이라서 됩니다. 어떤 일이냐면 세 가지를 갖춘 일입니다. 첫째, 목표가 숫자입니다. 설치 크기, 모델 크기, 메모리, 지연. 줄었는지는 재 보면 바로 압니다. 둘째, 기준이 분명합니다. 줄인 모델의 정확도가 원본만큼 나와야 한다. 통과인지 실패인지 애매할 게 없습니다. 셋째, 정답을 이미 가지고 있습니다. 원본 모델이 정답지입니다. 같은 문장을 원본과 줄인 모델에 넣어서 벡터가 같은지만 비교하면 됩니다. 이렇게 목표와 기준이 분명하고 정답이 있는 일은 에이전트에게 던져 주면 정말 잘합니다. 변환하고, 재고, 정답과 비교하고, 안 맞으면 다른 방법을 시도하는 걸 스스로 반복하거든요. 제가 한 일은 무엇을 줄일지, 정확도를 어디까지 지킬지 정하고, 마지막에 비교표를 보고 무엇을 내보낼지 고른 것입니다. 반대로 목표가 흐릿하거나 정답을 모르는 일은 에이전트도 헤맵니다. 이 차이를 알아 두시면 다른 업무에도 써먹을 수 있습니다.

쓰지 않는 행을 뺄 뿐 남은 가중치는 그대로라 결과가 같다. 대가는 범용성: 한국어 법령 전용 모델이 된다.

uv run ragkit prune-vocab models/multilingual-e5-small → export-onnx → quantize · 실험 008

세 번째는 어휘 가지치기입니다. 모델을 열어 보면 파라미터의 82%가 단어 임베딩 표입니다. 다국어 모델이라 100개 언어의 어휘 25만 개를 들고 있죠. 층을 줄이기 전에 어휘부터 봅니다. 법령 코퍼스와 한글 조각, 짧은 기호만 남기면 약 1만 9천 개로 줄고, INT8 모델이 118MB에서 30MB가 됩니다. 양자화와 달리 가지치기는 쓰지 않는 행을 빼는 것이라, test 질문 전부가 원본과 똑같이 토큰화됐습니다. 대신 한국어 법령 전용 모델이 됩니다. 실제 사용자 질문을 얼마나 덮는지는 꼭 확인해야 합니다.

범용성: 한국어 법령 전용

무엇을 내보낼지는 표가 아니라 쓰임새가 정한다. 그 판단이 DS의 일이다.

표를 판단으로 바꿔 봅니다. 가지치기에 INT8을 더하면 설치, 모델, 메모리, 로딩이 몇 분의 일로 줄고 정확도는 같습니다. 잃는 것도 있습니다. 느린 쪽 지연이 늘고, 문서를 대량으로 임베딩하는 처리량이 절반으로 줄고, 한국어 법령 전용이 됩니다. 질문 하나씩 검색하는 서비스에 34ms는 문제가 안 될 수 있지만, 인덱스를 자주 새로 만들어야 한다면 이야기가 다릅니다. 어느 쪽을 내보낼지는 쓰임새를 보고 DS가 정합니다.

API에 적용

고른 모델로 바꿔 띄운다

# 처음: torch 백엔드
uv run --package ragkit-api ragkit-api --backend torch
# 지금: 가지치기 + INT8 모델
uv run --package ragkit-api ragkit-api --model models/multilingual-e5-small-pruned-int8

바뀌는 건 옵션 하나

API 코드는 그대로다. 이 30MB 모델을 8교시에 세 가지 길(HTML 파일 하나 · 웹 · 에이전트)로 건넨다.

고른 모델로 API를 다시 띄웁니다. 옵션 하나만 바뀌고 API 코드는 그대로입니다. 3번 스크립트가 백엔드를 바꿔 가며 시작 시간과 검색 속도를 직접 재는데, 여기 띄우는 가지치기 + INT8 모델 기준으로, 이 Mac에서는 시작 시간이 torch의 약 3.3초에서 0.1초로, 워밍업 후 20회 검색 중앙값이 약 15ms에서 9ms로 줄었습니다. 가지치기 없이 ONNX INT8만 쓰면 시작은 0.3~0.4초입니다. 돌릴 때마다 조금씩 달라지니 범위로 기억하세요. 이 모델을 8교시에 HTML 파일 하나, 웹, 에이전트, 세 가지 길로 사용자에게 건넵니다.

--run은 임시 폴더에서 처음부터 직접 (02 약 30초 · 03 약 1분, 받은 파일은 그대로).

위에서부터 순서대로 돌립니다. 1번은 API 복습입니다. 2번은 ragkit 명령 다섯 줄로 ONNX 변환, 채널별 INT8 양자화, 어휘 가지치기 뒤 다시 변환과 양자화를 해서 배포용 모델 세 개를 만들고, 02 스크립트로 만든 모델을 비교합니다. 3번은 새 모델마다 코퍼스 2.6만 문서를 다시 임베딩해 인덱스를 만들어야 해서 몇 분씩 걸립니다. 쉬는 시간 전에 걸어 두세요. 그다음 03 스크립트로 비교표를 읽고 API 백엔드를 바꿔 시작 시간과 검색 속도를 잽니다. 직접 해 보고 싶으면 --run을 붙이세요. 2번은 임시 폴더에서 ONNX 변환, 텐서 단위와 채널별 양자화, 어휘 가지치기를 직접 하고, 3번은 test 질문 200개로 ragkit-bench를 다시 잽니다. 2번 --run은 약 30초, 3번 --run은 약 1분 걸리고, 받은 모델과 결과는 덮어쓰지 않습니다. 선택: uv run python lecture/07_optimize/extra_embedding_speed.py (약 2분)

내 쓰임새라면 어느 변형을 고를지, 그 이유 한 줄

API 시작 · 검색 속도

torch에서 바꾸면 시작 약 3.3s → ONNX INT8 0.3s · 가지치기+INT8 0.1s, 검색 약 15 → 9ms (워밍업 후 20회 중앙값, 이 Mac)

세 가지를 확인합니다. 변환한 모델이 원본과 같은 결과를 내는지, 비교표를 보고 내 상황이라면 무엇을 고를지 한 줄로 써 보기, 그리고 3번 스크립트에서 API를 torch, ONNX INT8, 가지치기 + INT8로 바꿔 띄웠을 때 시작 시간과 검색 속도입니다. 검색은 첫 요청을 워밍업으로 버리고 20회 잰 중앙값인데, 이 Mac에서는 torch로 약 3.3초 걸리던 시작이 ONNX INT8에서 0.3~0.4초, 가지치기 + INT8에서 0.1초로 줄었고, 검색은 약 15ms에서 9ms로 줄었습니다. 여러분 노트북에서는 숫자가 다를 수 있습니다.
