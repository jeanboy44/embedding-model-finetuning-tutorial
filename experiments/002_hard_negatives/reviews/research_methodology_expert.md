# 001 리서치 검토 — 실험 방법론

검토 대상: `00_error_analysis.md`, `01_research.md`. 확인용 계산(exp_009 dev eval JSON, train top-50)은 이 검토에서 직접 했다.

## 0. 먼저 알아야 할 숫자 두 개

- **법령 군집 표준오차는 ±0.040이다.** 질문 단위 bootstrap으로는 ±0.012이지만, 9개 법령을 다시 뽑는 bootstrap에서는 ±0.040이 나온다. ±0.012는 "이 dev에서 두 모델 중 어느 쪽이 나은가"를 판단하는 오차이고, "처음 보는 법령에서 일반화되는가"의 오차는 그보다 3배 크다. 지방세법(505문항, R@5 0.687)과 할부거래법(0.476)이 micro 값을 좌우한다. micro와 법령 평균이 0.729와 0.762로 갈린다.
- **train 채굴 후보의 19%가 dev·test 법령 문서다.** top-30 기준 dev 7%, test 12%다. 3절에서 다룬다.

## 1. dev로 채굴 하이퍼파라미터를 고르는 것

허용한다. 다만 조건이 있다. 지금 dev는 epoch 선택, 0단계 필터 검증, 에러 분석에 이미 쓰였고, 앞으로 3~5단계에서도 계속 쓰인다. 비교가 쌓일수록 dev 최고값은 위로 치우친다.

안전장치:
1. **기본값을 사전 등록한다.** 문헌값(95% relative margin, 상위 1~10위 위주, negative 4~7개)을 `02_plan.md`에 고정하고, 이 설정으로 주 실행 1회를 돌린다. dev 탐색 없이 정한 값이다.
2. **비교 예산을 정한다.** 이번 실험에서 dev로 비교할 변형은 최대 3개로 한다(예: negative 수 4 대 7, 다른 법령 포함 여부). 변형마다 기준선 대비 검정을 하고 Holm 보정을 쓴다. 예산을 넘는 탐색은 다음 실험으로 넘긴다.
3. **두 번째 검증 세트(선택)를 둔다.** 앞으로도 탐색을 많이 할 계획이라면 train 법령 3~4개(약 800~1,000문항, 지방세법과 겹치지 않는 테마를 섞어서)를 떼어 val2로 둔다. val2로 하이퍼파라미터를 고르고, dev로는 통과 여부만 판정한다. 이렇게 하면 기준선(exp_009)도 줄어든 train으로 다시 학습해야 한다. 비용이 들기 때문에 2번의 예산으로 충분하면 생략해도 된다.
4. **epoch 선택 규칙을 같게 한다.** 기준선과 새 모델을 모두 "dev best epoch(최대 4)"로 고르거나, 모두 같은 epoch로 고정한다. 최고값끼리 비교하면 최댓값 편향이 양쪽에 같이 들어간다.

## 2. 개선을 주장하기 위한 최소 증거

per_question의 `multi_rank`로 질문별 hit@5(0/1) 쌍을 만든다. 공식 수치는 `ragkit evaluate` 값만 쓴다. 학습 중 간이 평가(0.721)와 공식 평가(0.729)는 계산 방식이 다르므로 섞지 않는다.

- **주 검정**: 대응 bootstrap(10,000회, 질문 재표집)으로 Δ의 95% CI를 구하고, McNemar exact 검정을 함께 본다. 서로 답이 갈리는 질문이 10% 정도라면 Δ의 대응 SE는 √(0.10/1412) ≈ 0.008이다. 비대응 ±0.012보다 민감하다.
- **보조**: 법령 군집 bootstrap CI, 9개 법령 중 나빠지지 않은 법령 수, MRR@10 대응 차이.
- **seed 분산은 한 번은 재야 한다.** exp_009 설정을 seed 2개로 더 학습한다(약 84분 × 2). 세 run의 dev R@5 표준편차가 σ_seed다. 이 값은 한 번 재 두면 이후 실험에서 다시 쓸 수 있다. 시간이 부족하면 새 설정만 seed 2개로 돌리고, 두 run이 모두 기준을 넘는지를 본다.
- **"개선"으로 판정하는 조건(모두 충족)**: (a) micro Δ ≥ 0.02, (b) 대응 bootstrap CI 하한 > 0, (c) Δ > 2σ_seed, (d) 법령 평균 Δ ≥ 0이고 9개 법령 중 6개 이상이 나빠지지 않음. 통과 기준 0.76은 +0.031이라서 위 조건을 만족하는 수준이다.

## 3. 누수 위험

1. **채굴 후보 범위 (가장 중요).** 코퍼스 전체에서 채굴하면 dev·test 법령 조문이 학습의 negative로 들어간다. dev 질문 자체는 보지 않지만, 모델이 dev 문서의 임베딩을 학습하게 된다. 이것은 "처음 보는 법령" 평가 조건(PLAN의 결정 A)을 깨는 전이(transductive) 노출이다. 주 실행은 **train 법령 문서만으로 채굴한다**. 코퍼스 전체 채굴은 별도 조건으로 돌리고, 결과표에 "결정 B 조건"이라고 표시한다. 다른 법령 negative의 효과도 train 법령 29개 안에서 충분히 잴 수 있다.
2. **Claude 판정.** train 질문과 train 법령 후보 쌍만 판정한다. dev·test 문서가 걸린 쌍은 판정하지 않는다. 프롬프트에는 질문과 후보 원문만 넣는다. 모델 점수, 순위, "원래 정답" 여부는 숨기고, 후보 순서는 섞는다. train 원래 정답 50개와 명백한 negative 50개를 섞어 판정 정확도를 재고, 100쌍은 두 번 판정해 일관성을 기록한다.
3. **dev 라벨을 고정한다.** `data/labels/dev.jsonl`의 해시를 기록하고, 이번 실험 동안 바꾸지 않는다. 새 모델의 상위 결과를 보고 dev 정답을 추가하면 그 모델에 유리하게 치우친다. 바꿔야 한다면 구조 기반 후보로만 고치고, 모든 모델을 다시 평가한다.
4. **dev에서 나온 규칙을 쓰지 않는다.** 단어 겹침 필터의 근거(버린 쌍 중 정답 0/100)는 dev에서 나왔다. 채굴에 쓰려면 train 표본 100건으로 다시 검증한다.

## 4. 로깅과 재현성 (`03_run/`, `artifacts/`)

- `config.yaml`: 채굴 모델 경로와 해시, 후보 범위, margin, negative 수, 샘플링 방식, 후보 풀(train 법령만 / 전체), seed, 학습 하이퍼파라미터
- `data_digest.json`: train/dev/test split, `dev.jsonl` 라벨, 코퍼스, 채굴 결과 파일의 sha256과 행 수, 데이터 버전, git commit, 라이브러리 버전
- `mined_negatives.jsonl`: qid, 후보 id, 순위, 점수, 정답 점수 대비 비율, 관계 분류(같은 법·종류 / 다른 법·테마 등), 필터 통과 여부, 최종 사용 여부
- `judgments.jsonl`: qid, 후보 id, 판정(full/partial/no), 근거 한 줄, 프롬프트 버전, 보정 세트 여부
- 학습 로그: epoch별 dev 공식 R@5(micro, 법령 평균), train 표본 R@5, loss, 실행 시간, 최대 메모리
- 평가: epoch별 eval JSON 전체와 기준선 대비 `paired_test.json`(Δ, CI, McNemar p, 법령별 Δ)
- **eval JSON의 per_question에 qid를 넣는다.** 지금은 query와 positive_id만 있어서 라벨이나 다른 run과 질문 텍스트로 이어 붙여야 한다. 질문별 top-10 id와 점수도 함께 저장하면, 05_retro에서 "고친 질문 / 새로 틀린 질문"을 실패 유형별로 바로 나눌 수 있다.

## 요약

dev로 채굴 설정을 고르는 것은 사전 등록과 비교 3개 예산 안에서 허용한다. 개선은 대응 bootstrap, McNemar, seed 분산, 법령별 일관성으로 판정한다. 채굴 후보는 train 법령 문서로 제한한다.
